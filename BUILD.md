# Выпуск версии

Поставка — это каталог `sf-form-sender/` и ничего больше. Всё в корне
репозитория (`tests/`, `tools/`, `build-zip.php`, `README.md`, `CLAUDE.md`,
`TEST-REPORT.md`, `BUILD.md`) — материал разработки, и в архив не попадает.

**Архив никогда не коммитится в репозиторий.** Его собирает
`.github/workflows/release.yml` и прикладывает к соответствующему GitHub
Release. Zip внутри дерева остался бы в истории git навсегда и рос бы с каждым
выпуском, поэтому `.gitignore` закрывает `*.zip` и `download/`.

## Как выпустить новую версию

1. Поднимите версию в **трёх** местах, они должны совпадать:
   - `sf-form-sender/sf-form-sender.php` — заголовок `Version:`
   - `sf-form-sender/sf-form-sender.php` — константа `SF_FS_VERSION`
   - `sf-form-sender/readme.txt` — `Stable tag:`
2. Допишите в `readme.txt` раздел `== Changelog ==` запись вида `= 1.1.0 =`
   с перечнем изменений.
3. Если менялись строки, которые видит человек, — обновите словари:
   ```bash
   python3 tools/build-languages.py     # соберёт .pot, дополнит .po, скомпилирует .mo
   # переведите новые строки в каждом languages/sf-form-sender-<locale>.po
   python3 tools/build-languages.py     # ещё раз: печатает, сколько осталось без перевода
   ```
   Сборка не станет ругаться на неполный перевод, но `build-zip.php` откажется
   собирать архив, если `.mo` старше своего `.po`.
4. Прогоните всё локально и запушьте:
   ```bash
   php tests/test-plugin.php
   python3 tests/test-front.py
   php build-zip.php
   ```
5. Выпустите — любым из двух способов:

   **Из вкладки Actions, без командной строки.** Откройте **Actions → Release →
   Run workflow**, выберите ветку с нужным коммитом, введите версию (`1.1.0`,
   с ведущей `v` или без) и нажмите **Run workflow**. Тег `v1.1.0` workflow
   создаст на этой ветке сам. Это весь выпуск, заранее ничего тегировать не
   нужно.

   **Либо запушив тег**, что запускает тот же workflow:
   ```bash
   git tag v1.1.0
   git push origin v1.1.0
   ```

Дальше workflow:

* сверяет тег, обе версии в файле плагина, `Stable tag:` в `readme.txt` и
  наличие записи в списке изменений — и отказывается выпускать, если они
  разошлись;
* собирает `SFformSender-<версия>.zip` тем же `build-zip.php`, которым вы
  пользуетесь локально, — то есть с проверкой полноты архива;
* проверяет архив: он открывается, в нём ровно один каталог верхнего уровня с
  именем `sf-form-sender`, и в нём нет ни `tests/`, ни `tools/`, ни точечных
  файлов;
* создаёт GitHub Release с приложенным архивом и его sha256 в описании.

Сверка версий идёт **до** создания тега, поэтому ручной запуск с версией, не
совпадающей с файлами плагина, падает, не оставив тега. Повторный запуск для
уже существующего тега переиспользует его и заменяет вложение, а не падает.

## Что проверяет `build-zip.php`

Он собирает архив и отказывается отдавать неполный. До сборки:

* версия в заголовке плагина и в константе `SF_FS_VERSION` совпадают;
* словарей `.mo` ровно семь;
* ни один `.mo` не старше своего `.po`.

После сборки он читает исходники, собирает все пути, встречающиеся в
`SF_FS_DIR` и `SF_FS_URL`, и сверяет с содержимым готового архива; проверяет,
что каждый php в архиве разбирается, и что главный файл с `uninstall.php` на
месте. Неполный архив удаляется, сборка завершается с ошибкой.

Забытый в архиве файл — это белый экран у того, кто ставит плагин с нуля.
Проверка идёт по коду, а не по памяти о составе.

## Сборка архива вручную

Нужна только для локальной проверки; сам выпуск всегда идёт через workflow.

```bash
php build-zip.php
unzip -l sf-form-sender.zip
```

В архиве должен быть ровно один каталог верхнего уровня, `sf-form-sender/`:

```
sf-form-sender/
├── sf-form-sender.php
├── uninstall.php
├── readme.txt
├── includes/
│   └── admin/
│       └── views/
├── assets/
│   ├── css/
│   └── js/
└── languages/
```

`languages/` везёт `.pot`, а также `.po` и скомпилированный `.mo` на каждый из
семи языков: так принято в каталоге плагинов WordPress, и так проще тому, кто
захочет поправить перевод у себя.

## Проверка архива

Поставьте его в WordPress и убедитесь, что активация проходит и таблицы
создаются:

```bash
wp plugin install sf-form-sender.zip --activate
wp eval-file tests/integration/smoke.php
```

Дымовая проверка `tests/integration/smoke.php` — та же, что гоняет CI: она
смотрит таблицы, настройки, каталог загрузок, сохраняет и удаляет заявку,
рисует обе страницы админки и проверяет, что все семь словарей грузятся.

Ставьте плагин настоящим каталогом, а не символической ссылкой: у ссылки
иначе разрешается `plugin_dir_url()`.
